# BSan builds regenerate different bindings, so campaign mode fails under BSan

Status: `open`: the campaign's fix landed as `47b4662c9`; the spec's half is to be made and reviewed.

## Signal

A gate that cannot run (`evolution` §2): `crustify/scripts/cargo-variant.sh bsan test --workspace
--no-run` fails in the raw bindings' build script, "bindings.rs does not match", on the working
branch before and after the bundling migration (`928aa1ba9`, `e11d5b3ae`), the two
regenerations byte-identical. `cargo bsan` forces `LIBCLANG_PATH` to BorrowSanitizer's own LLVM,
whose libclang adds 27 doc-comment lines on macro constants; setting `LIBCLANG_PATH` does not
override it. With `CRUSTIFY_BINDINGS_UPDATE=1` all six test executables build and link.

This is the `bindgen` skill's open TODO, "the libclang that generates the bindings is not pinned
yet, though a regenerated binding must match the committed one byte for byte", met.

## Destination

The spec (`bindgen` Generation: the libclang is pinned, and campaign mode generates with it
whatever toolchain drives the build) and the campaign's build script.

## Change

The campaign's half, `47b4662c9` on the working branch (2026-11-13):

- **Cause.** bindgen 0.73.2 loads libclang at run time through clang-sys 1.9.1 (`runtime`
  feature), from `LIBCLANG_PATH` when set, else `llvm-config --prefix` and the standard dirs,
  highest version first; it runs a clang for the system include dirs from `CLANG_PATH`, else
  `llvm-config --bindir`, else `PATH`. `cargo bsan` sets both for every build script, overriding
  the caller's (`/root/.rustup/toolchains/bsan/lib`, libclang 23.1.3, and its `clang-23`). The
  committed bindings were generated by LLVM 18.1.3 (`/usr/lib/llvm-18`, Ubuntu's package), which
  every other driver reached only through the ambient `LIBCLANG_PATH`: unset, clang-sys would
  have picked the highest installed LLVM.
- **Pin.** `Cargo.toml`'s `[workspace.metadata.crustify]` records `bindgen-llvm =
  "/usr/lib/llvm-18"` and `bindgen-llvm-version = "18.1.3"`, beside the nightly and the exact
  bindgen.
- **Enforcement.** In campaign mode, when the `bindgen` feature regenerates, `build.rs`'s
  `pin_llvm` runs first in `main`, before any thread: it checks `<prefix>/lib/libclang.so` exists
  and `<prefix>/bin/clang --version` reports the pinned version, then sets `LIBCLANG_PATH` and
  `CLANG_PATH` to them in its own process. Another version or a missing LLVM fails the build,
  naming both. The byte-for-byte comparison is unchanged, doc comments included; a dependent's
  bundled or shared regeneration, into `OUT_DIR` and compared with nothing, is not pinned.

The spec's half, still to make: `bindgen`'s Generation TODO is replaced by the rule: the LLVM
that generates the bindings is pinned with the bindgen version, campaign mode loads that
libclang and runs that clang whatever drives the build, and a build under another fails.

## Validation

On the fix's tree: fmt and plain clippy (warnings denied) pass; `CRUSTIFY_BUILD_VARIANT=plain
CRUSTIFY_BINDINGS_UPDATE= cargo build --features bindgen` leaves both units' bindings unchanged;
`cargo-variant.sh bsan test --workspace --no-run` builds its 6 test executables without
`CRUSTIFY_BINDINGS_UPDATE` (it failed before); asan-ubsan, tsan, coverage and Miri `--no-run`
build theirs; plain `test --workspace --no-fail-fast`: 2,759 passed, 0 failed, 1 ignored. A pin
set to 23.1.3 fails the build naming the pinned and found versions.
