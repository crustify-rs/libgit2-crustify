# `SHA1_DVS` loses its `sha1_dvs` alias, and its description, once the export feature is on

**Where.** `src/libgit2/src/util/hash/sha1dc/ubc_check.rs` on `e816c88bb`. The table has two
definitions, one per state of the export feature:

```rust
/// The disturbance vectors SHA-1 collision detection checks, generated by `parse_bitrel` …
///
/// Replaces `glb::sha1_dvs`
#[doc(alias = "sha1_dvs")]
#[cfg(not(feature = "ffi-export-src-util-hash-sha1dc-ubc-check-c"))]
pub static SHA1_DVS: [DvInfo; DV_COUNT] = DVS;

#[cfg(feature = "ffi-export-src-util-hash-sha1dc-ubc-check-c")]
pub use self::ffi_export::sha1_dvs as SHA1_DVS;
```

**What is wrong.** The conventions' Anchors section gives the item that stands in for a C item
two attributes, the anchor and the alias, "so that a consumer who searches the documentation
for the source's name finds every item that stands in for it". With the feature off,
`SHA1_DVS` has both. With it on, `SHA1_DVS` is the re-export of the gateway's
`#[unsafe(no_mangle)] pub static sha1_dvs`, whose documentation carries the anchor but cannot
carry the alias, since rustdoc rejects an alias equal to its item's own name, and the re-export
carries neither an alias nor a word of documentation of its own. Rustdoc inlines the re-export
of an item of a private module under the re-export's name, `SHA1_DVS`, so a search for
`sha1_dvs` no longer finds it, and its page holds only the gateway's text, which describes the
storage `sha1.c` reads and not the table the native API offers.

The feature is off in every build until the module's switch, and the switch, which follows
this pass, deletes it together with the `cfg(not(…))` static: from then on the re-export is
the table's only definition, and the alias and the description would be gone from the crate's
documentation for good. Nothing a consumer's code can observe; hence `nit`, with no reproducer.

**Check.** A crate that re-exports a `no_mangle` static of a private module, with and without
`#[doc(alias = "sha1_dvs")]` on the `pub use`: the alias reaches the search index only with
it (`rustdoc 1.100.0 (0ef1bc386 2026-11-09)`: an index file names `sha1_dvs` with it, none
without it):

```
mkdir -p /tmp/alias && cd /tmp/alias
cat > lib.rs <<'EOF'
//! x
mod inner {
    /// The table.
    #[unsafe(no_mangle)]
    pub static sha1_dvs: [u32; 2] = [1, 2];
}
/// The re-export's own doc.
#[doc(alias = "sha1_dvs")]
pub use self::inner::sha1_dvs as SHA1_DVS;
EOF
sed '/doc(alias/d' lib.rs > lib2.rs
rustdoc --edition 2024 --crate-type lib lib.rs -o with
rustdoc --edition 2024 --crate-type lib --crate-name lib lib2.rs -o without
grep -rl sha1_dvs with/search.index | wc -l      # 1
grep -rl sha1_dvs without/search.index | wc -l   # 0
```

In the crate itself the index names `sha1_dvs` with the feature on at `e816c88bb` too, as the
raw binding `sys::libgit2::sha1_dvs`, which is not the item a consumer uses in place of the C
global.

**Fix.** The re-export takes `#[doc(alias = "sha1_dvs")]` and the first paragraph of the
native static's description, which rustdoc shows before the gateway's text, so that with the
feature on `SHA1_DVS` has the alias, the description and, from the gateway, the anchor once
each. At the switch, the `cfg(not(…))` static goes and the re-export keeps all three.

**Tiers.** Caught by this module pass (`wave-221/batch-3`), the first review tier of the
code: `wave-221/batch-1`'s own gates had it in scope, and lint with the feature on, which
does not check anchors.
